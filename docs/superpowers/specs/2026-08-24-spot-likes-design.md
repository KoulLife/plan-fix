# 스팟 좋아요 기능 설계

작성일: 2026-08-24

## 배경

`spots.like_count`는 이미 있고 인기순 정렬(`sort=popular`)의 가중치로도 쓰이고 있지만,
지금까지 이 값을 실제로 올리는 경로가 없었다. "어떤 사용자가 어떤 스팟을 좋아요했는지"
이력이 없으면 중복 좋아요를 막을 수도, 좋아요를 취소할 수도, 사용자에게 하트를 채워
보여줄 수도 없다. `users`와 `spots`를 잇는 새 테이블이 필요하다.

## 목표

- 로그인한 사용자가 스팟을 좋아요/좋아요 취소할 수 있다.
- 같은 사용자가 같은 스팟을 두 번 좋아요해도 카운트가 두 번 올라가지 않는다.
- 동시 요청(따닥 클릭, 네트워크 재시도)에도 카운트가 어긋나지 않는다.
- 상세 조회 시 로그인한 사용자가 이미 좋아요했는지 알 수 있다(`isLiked`).

## 비목표

- 이번 범위는 백엔드까지다. 프론트엔드 하트 버튼 연동은 별도로 진행한다.
- 좋아요 알림, 좋아요한 사람 목록 조회, "내가 좋아요한 스팟 목록" API는 이번 범위 밖이다.
- `spot_likes`를 감사 로그처럼 영구 보존할지(취소해도 행을 지우지 않고 상태만 바꿀지)는
  다루지 않는다 — 취소 시 행을 실제로 삭제하는 단순한 모델로 간다.

## 데이터 모델

`spot_likes` — `users`와 `spots`의 다대다 관계를 표현하는 이력 테이블.

| 컬럼 | 타입 | NULL | 비고 |
|---|---|---|---|
| `spot_like_id` | bigint | NOT NULL | PK, identity |
| `user_id` | bigint | NOT NULL | FK → users(user_id) |
| `spot_id` | bigint | NOT NULL | FK → spots(spot_id) |
| `created_at` | timestamptz | NOT NULL | |

`UNIQUE (user_id, spot_id)` 제약을 건다. 이 제약이 "이 사용자가 이 스팟을 좋아요했는가"의
유일한 진실 소스이자, 동시 요청으로 인한 중복 좋아요를 DB 레벨에서 막는 안전장치다.

`spots.like_count`는 지금처럼 비정규화된 카운터로 유지한다. `spot_likes`에서
`COUNT(*)`로 매번 계산하지 않고, 좋아요/취소 시점에 `view_count`와 같은 방식으로
원자적 UPDATE(`SET like_count = like_count ± 1`)로 증감시킨다 — 인기순 정렬이 이
컬럼을 직접 참조하므로 조회 경로에 조인을 추가하고 싶지 않다.

로컬은 `ddl-auto: update`가 새 테이블을 자동으로 만들어 주지만, 운영은
`ddl-auto: validate`라 스키마 변경이 자동 반영되지 않는다. 그래서 이번에도
`docs/migrations/2026-08-24-create-spot-likes.sql`을 만들어 둔다.

```sql
CREATE TABLE IF NOT EXISTS spot_likes (
    spot_like_id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id BIGINT NOT NULL REFERENCES users(user_id),
    spot_id BIGINT NOT NULL REFERENCES spots(spot_id),
    created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT uq_spot_likes_user_spot UNIQUE (user_id, spot_id)
);
CREATE INDEX IF NOT EXISTS idx_spot_likes_spot_id ON spot_likes(spot_id);
```

## API

### `POST /api/v1/spots/{spotId}/like`

로그인 필요(`SecurityConfig`가 스팟 GET만 `permitAll`이라 이 경로는 별도 설정 없이
기본 규칙(`anyRequest().authenticated()`)에 걸려 자동으로 인증을 요구한다).

- 스팟이 없거나 `status=HIDDEN`이면 404.
- 이미 좋아요한 상태면 아무것도 하지 않고 현재 상태를 그대로 응답한다(idempotent).
- 응답: `{ "liked": true, "likeCount": 4 }`

### `DELETE /api/v1/spots/{spotId}/like`

- 좋아요하지 않은 상태에서 호출해도 조용히 무시하고 현재 상태를 응답한다(idempotent).
- 응답: `{ "liked": false, "likeCount": 3 }`

### `GET /api/v1/spots/{spotId}` (기존 API 확장)

응답에 `isLiked` 필드를 추가한다. 로그인 상태면 실제 값, 비로그인이면 `false`.
이 엔드포인트는 `permitAll`이지만 `JwtAuthenticationFilter`는 모든 요청에서 실행되므로,
유효한 `access_token` 쿠키가 있으면 비로그인 전용 경로에서도 `SecurityContext`에
인증 정보가 채워진다 — 그 정보로 viewer의 좋아요 여부를 판단한다.

## 동시성

"좋아요했는지 확인 → 없으면 insert" 사이에는 레이스가 있을 수 있다(따닥 클릭, 네트워크
재시도). `(user_id, spot_id)` 유니크 제약을 걸어 두고, insert가
`DataIntegrityViolationException`으로 실패하면 "이미 좋아요됨"으로 간주해 카운트
증가를 건너뛴다 — 카카오 소셜 로그인의 동시 첫 로그인 처리와 같은 패턴이다
(`SocialLoginApplicationService`).

취소(`decrementLikeCount`)는 `CASE WHEN like_count > 0 THEN like_count - 1 ELSE 0 END`로
0 밑으로 내려가지 않게 가드한다. delete가 실제로 행을 지웠을 때만 감소시키고, 지울 행이
없었으면(이미 취소된 상태) 감소도 생략한다.

## 미해결/향후 과제

- "내가 좋아요한 스팟 목록" 조회 API는 이번 범위 밖. 필요해지면
  `SpotLikeRepository.findByUserId(Long userId)`를 추가하는 정도로 확장 가능하다.
- 좋아요 취소 시 행을 삭제하는 대신 상태 필드로 남기는 이력 보존 방식은 다루지 않았다.
  분석/추천 용도로 "좋아요했다가 취소한 이력"이 필요해지면 재검토한다.
